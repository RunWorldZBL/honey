# 长按语音分段识别预览设计

## 1. 背景

honey 当前的长按说话流程是：用户按住热键开始录音，松开热键后结束录音，再把整段音频送给语音转文字模型处理，最后一次性上屏并写入历史。

这个流程适合短句，但当用户连续说 5 到 10 分钟时，等待会集中发生在松开按键之后。用户在长时间说话过程中自然会停顿、思考或换气，这些空隙可以被利用起来，把已经稳定的前置语音片段提前送去识别，从而降低最终松开后的等待感。

本设计只解决“长按期间分段识别和 bar 预览”的体验与技术方案，不处理标点模型能力本身。标点符号能力需要另行参考 `D:\app\musicWS\CapsWriter-Offline` 的实现方式，确认它使用的模型、解码器或后处理链路。

## 2. 已确认方案

采用“分段识别预览，松开统一上屏”。

用户按住热键后，honey 持续采集语音，并根据音量和静音时长判断是否出现自然停顿。当检测到约 1.2 到 1.5 秒静音时，默认按 1.3 秒，把静音前已经稳定的一段音频提交给语音转文字模型后台识别。

中途识别结果不写入输入框，只在屏幕底部的 bar 中显示最新识别完成的原文片段。用户再次说话时，bar 立即回到音频可视化状态。

用户松开热键后，honey 等待所有已提交片段和最后残留片段识别完成，合并成完整文本，再一次性写入当前输入框，并写入历史记录。

## 3. 非目标

- 不做中途识别完成后立刻写入输入框。
- 不在 bar 中显示累计全文。
- 不在 bar 中显示实时人设改写结果。
- 不把标点符号能力误实现为“只靠停顿补标点”。
- 不在第一版实现复杂的用户确认、撤销或分段编辑面板。

## 4. 交互规则

### 4.0 典型时序

1. 用户按住热键开始说话，bar 显示音频可视化。
2. 用户停顿约 1.3 秒，原生录音层切出前一段音频。
3. 前一段音频被提交到后端分段识别队列，产生 `segmentCreated` 事件或等价返回。
4. 如果 ASR 在用户继续说话时返回 `segmentRecognized` 结果，bar 继续显示音浪，结果先缓存。
5. 用户下一次停顿时，bar 显示最新识别完成的原文片段。
6. 用户继续说话，bar 立即回到音频可视化。
7. 用户松开热键，尾段被提交识别。
8. 后端等待所有片段完成，合并完整原文。
9. 直接转写模式插入合并原文；人设模式先对完整原文做人设处理，再插入处理后的文本。
10. bar 展示本次最终插入文本后自动隐藏。

### 4.1 按住热键

用户按住热键时，bar 显示音频可视化。检测到声音时音浪跳动；没有声音时保持低幅或静止状态。

### 4.2 停顿切片

当连续静音达到默认 1.3 秒时，系统认为前一段语音已经稳定，可以切成一个待识别片段。切片后继续保持当前录音会话，用户不需要松开热键。

静音触发阈值应预留为配置项，后续可命名为“分段识别灵敏度”或“停顿识别时间”。

### 4.3 识别结果预览

识别完成后，bar 只显示最新识别完成的原文片段。

“最新”按片段顺序判断，而不是按 ASR 返回时间判断。即使第三段比第二段先识别完成，bar 也不应该跳过第二段直接展示第三段，避免用户看到的预览顺序和自己说话顺序不一致。第一版识别并发为 1 时天然满足这个规则。

如果识别结果返回时用户正在说话，bar 不打断音浪，先缓存结果。等用户再次进入停顿状态时，再短暂展示这条最新片段。

如果用户在停顿状态下看到预览后继续说话，bar 立即切回音频可视化。

### 4.4 松开热键

用户松开热键后：

1. 停止继续采集音频。
2. 把最后一段尚未提交的音频作为尾段提交识别。
3. 等待所有片段识别完成。
4. 按原始顺序合并片段文本。
5. 根据当前模式生成最终输出。
6. 一次性插入当前输入框。
7. 写入历史记录。
8. bar 展示最终插入文本后自动隐藏。直接转写模式展示合并原文；人设模式展示人设处理后的最终文本。

## 5. 直接转写与人设模式

### 5.1 直接转写模式

中途 bar 显示每次分段识别出来的 ASR 原文片段。松开后合并完整 ASR 原文，一次性上屏。

### 5.2 人设模式

人设模式下，中途 bar 仍然只显示 ASR 原文片段。这样用户可以确认软件是否听清了自己，而不是被实时改写结果干扰。

松开后，系统先合并完整 ASR 原文，再把完整原文交给当前人设处理。最终上屏的是人设处理后的文本。

bar 不显示实时人设改写结果，因为这会增加等待、上下文不一致和认知负担，可能带来负增益。

## 6. 文本合并规则

片段合并应保持“忠实原文优先”。系统不应该为了美化文本而大幅改写用户内容。

基础规则：

- 按片段产生顺序合并。
- 每个片段保留模型输出文本。
- 如果片段自身已经带有标点，不重复补标点。
- 标点符号恢复能力需要单独调研 CapsWriter-Offline，确认是否应接入 `Fun-ASR-Nano-Decoder.q8_0.gguf` 或其它解码/后处理流程。

注意：用户已明确指出，当前没有标点的问题不应简单归因于停顿切片，也不应只靠停顿来构造标点。分段方案和标点恢复是两个独立问题。

因此，本方案的“合并”只负责把片段按顺序连接成完整文本，不负责根据停顿主动创造句号、逗号或语气标点。最终文本有没有标点，应优先由语音转文字模型、解码器或独立标点恢复链路决定。

## 7. 状态模型

建议在现有 `DictationOverlaySnapshot` 基础上增加能够表达分段预览的内部状态，但 UI 仍保持小胶囊形态。

推荐状态：

- `listening`：正在接收语音，显示音浪。
- `silent`：按住中但当前静音，音浪低幅或静止。
- `segmentRecognizing`：后台正在识别某个已切片片段，bar 可保持音浪或静默外观，不强制显示文字。
- `segmentPreview`：显示最新识别完成的原文片段。
- `recognizing`：松开后正在等待所有片段和尾段识别完成。
- `completed`：最终文本已生成。
- `inserted`：最终文本已上屏。
- `failed`：识别或插入失败。

UI 可以不把所有内部状态都展示成不同样式，但数据层需要能区分“整段最终识别”和“中途片段识别”。

## 8. 数据流

推荐拆成三个边界清晰的模块：

### 8.1 原生录音与切片

Tauri/Rust 侧继续负责 Windows 原生录音、音量采样和热键事件。新增一个会话级录音缓冲区，根据 RMS 音量和静音时长切出片段。

每个片段需要带上：

- `segmentId`
- `sessionId`
- `startedAtMs`
- `endedAtMs`
- `audioPath` 或内存音频数据
- `state`

Rust 侧只负责录音、音量、切片和片段文件落盘，不负责调用 ASR，也不负责最终文本合并。

片段产生后，Rust 侧通过 Tauri command 返回或事件通知前端。建议事件载荷至少包含 `sessionId`、`segmentId`、`startedAtMs`、`endedAtMs` 和 `audioPath`。

### 8.2 分段识别调度

后端 Node.js 服务负责维护分段识别队列、片段状态、识别结果、最终合并、人设处理和历史记录写入。

前端只负责把 Tauri/Rust 产出的片段提交给后端，并根据后端返回或推送的片段结果更新 bar。前端不持久化片段队列，也不负责最终文本合并。

片段产生后进入后端队列，识别成功后保存文本，失败后记录错误。

第一版建议限制并发为 1。这样顺序最稳定，CPU 占用也更可控。后续如果模型支持并行，再考虑并发。

建议后端提供或预留以下会话接口：

- `createSegment(sessionId, segment)`：接收新音频片段并入队。
- `segmentRecognized(sessionId, segmentId, text)`：内部状态或推送事件，用于通知前端最新可预览片段。
- `finalizeSession(sessionId, tailSegment?)`：松开热键后提交尾段，等待所有片段完成，并返回最终可插入文本。

### 8.3 最终合并与上屏

松开热键后，前端通知后端 finalize 当前 session。后端等待所有片段完成，按顺序合并文本。直接转写模式直接返回合并文本；人设模式把合并原文交给人设处理后再返回最终文本。

前端拿到最终文本后调用桌面插入能力，一次性上屏。

历史记录应保存完整会话结果。后续如果需要调试，可以在本地日志中保留片段级信息，但不一定在 UI 历史记录中展示每个片段。

## 9. 错误处理

### 9.1 单个片段识别失败

如果中途某个片段失败，bar 不应立即打断用户。第一版采用保守策略：任一片段识别失败，则本次会话在松开并 finalize 后整体失败，不插入部分文本。

这样可以避免新增 `partial_failed` 状态、避免把不完整文本误上屏，也让历史记录仍使用现有 `completed` / `failed` 状态模型。后续如果需要更强的容错，再单独设计“部分成功”状态和 UI 提示。

### 9.2 用户快速松开

如果用户按住时间很短，没有形成可识别片段，则走当前短句流程：松开后把完整录音作为单段识别。

### 9.3 识别慢于用户说话

如果 ASR 处理速度跟不上用户说话，bar 仍以音浪为主，不频繁切换到文字。识别结果可以排队缓存，最终松开后统一等待。

## 10. 设置项建议

第一版只内置默认值，不新增设置页 UI，也不新增持久化设置字段。

内置默认值：

- 静音触发时间，默认 1300 ms。
- 最短片段时长，默认 700 ms，避免切出过短语音。
- 分段识别并发数，默认 1。

第一版不做“最大片段时长强制切片”。如果用户连续说话且没有达到静音阈值，系统不应在用户仍在说话时强行截断音频；这会破坏语义连续性，也可能降低 ASR 质量。连续长语音会保留为当前活动片段，直到下一次自然停顿或用户松开热键后再作为尾段提交。

后续如需加入安全保护，可以增加“软最大片段时长”：超过指定时长后只在下一次静音或松开时切片，不在检测到持续语音时强制切断。这不进入第一版实现范围。

后续可以再把这些默认值暴露到设置页，例如“是否启用分段识别预览”“停顿识别时间”“分段识别并发数”。这些不进入第一版实现范围。

## 11. 验收标准

- 用户按住热键说话时，bar 显示音频可视化。
- 用户停顿约 1.3 秒后，前一段语音会进入后台识别。
- 中途识别完成后，bar 只显示最新原文片段。
- 用户继续说话时，bar 立即回到音频可视化。
- 中途识别结果不会写入输入框。
- 松开热键后，等待全部片段和尾段识别完成，再一次性上屏完整文本。
- 直接转写模式最终上屏合并后的 ASR 原文。
- 人设模式中途只预览 ASR 原文，最终上屏人设处理后的完整文本。
- 长语音场景下，松开后的等待时间明显低于整段结束后才开始识别。

## 12. 待单独调研：标点符号能力

用户指出 CapsWriter-Offline 在本机启动后可以输出标点，因此 honey 当前无标点不应被简单解释为“模型天生不支持”或“用停顿补标点即可”。

后续需要单独查看：

- `D:\app\musicWS\CapsWriter-Offline` 使用的 ASR 模型文件。
- 是否使用 `Fun-ASR-Nano-Decoder.q8_0.gguf`。
- 是否有独立的标点恢复模型、语言模型解码器或规则后处理。
- 它的实时听写链路是否把 encoder、CTC、decoder 串起来。
- honey 当前 Fun-ASR-Nano CTC 直出路径与 CapsWriter-Offline 的差异。

这项调研应作为下一步独立任务，不能混入本设计的分段识别预览范围。
